# Agent Instructions

## Task tracking

This project uses **kanban-md** for task management. Always follow the workflow defined in [`KANBAN.md`](./KANBAN.md): create a task per slice, claim it before coding, and move it to `done` only after `photo-reviewer` returns `VERDICT: PASS`. Keep the board and the code in sync at all times.

## Source of truth

**The kanban board is the source of truth.** Each task body carries its own goal, verified context, acceptance criteria and known traps — read the task first, and treat it as sufficient. Work is grouped into epics (parent tasks tagged `epic`); epics are never implemented directly, only their child slices are.

[`PLAN.md`](./PLAN.md) is the background: the product's reasoning, domain model, business rules and phasing. Read it for _why_. When the board and the plan disagree, the board wins — and the drift gets written into the task body so it stays visible. That has already happened once: the identity model collapsed `clients` into `users`, deviating from `PLAN.md` §6 for a reason recorded in the code and the commit.

Priority order is set by the project owner and overrides the plan's own sequencing: **the admin dashboard first, the public site last.**

## Verification is not optional

Nothing is "done" because it compiles. Before closing a slice:

```bash
bun run typecheck && bun run lint && bun run format:check && bun run test
```

All four, not three. `.github/workflows/ci.yml` runs `lint`, `format:check`,
`typecheck`, `test` and `build`, and `format:check` runs _before_ `typecheck` and
`test` — a formatting slip fails the build before the rest of the suite is ever
reached, so a green `typecheck && lint && test` locally tells you nothing about
that gate. Task #101 shipped red on exactly this omission.

And for anything touching a route, a build-time import, or the environment, reproduce the CI build in a clean worktree — the local `.env.local` hides this entire class of failure:

```bash
git worktree add /tmp/ci-check <branch> && cd /tmp/ci-check && bun install && bun run build
```

### Fresh worktrees: hooks do not protect you

`core.hooksPath` is `.husky/_`, generated by the `prepare: husky` script — which
only runs on `bun install`. A worktree created by the agent harness
(`.claude/worktrees/agent-*`) starts with no `node_modules` and therefore no
`.husky/_`. Git resolves a `core.hooksPath` pointing at a missing directory by
**silently doing nothing** — no error, no warning, the commit just succeeds
without `lint-staged` ever running `eslint --fix` or `prettier --write`. See #123
and the "Running lanes in parallel" section of `KANBAN.md`.

Run `bun install` in your own worktree before your first commit, or run
`.husky/verify-hooks.sh` to check explicitly — it fails loudly and tells you
exactly what is missing instead of letting the gap ride silently into CI.

**Decision (recorded 2026-07-30, #123):** we do not attempt to make git fire the
hook automatically before install. `core.hooksPath` is shared repository config —
verified identical from two different worktrees, with `extensions.worktreeConfig`
unset — so changing where it points would change hook behaviour for every
worktree at once, including whichever lanes are active at the time. That blast
radius is not something a single slice should take on. We also do not switch this
project wholesale to the out-of-repo `lane-*` convention (`.photo-worktrees/lane-*`):
those worktrees stay installed only because they are long-lived and happen to have
had `bun install` run once early on, not because of anything structural, and
migrating the harness is outside this repo's control anyway. Instead we keep the
gap procedural and loud: `bun install` first, `verify-hooks.sh` as a fast explicit
check, and `format:check` in the standing checklist as the defense-in-depth that
catches anything that still slips through.
